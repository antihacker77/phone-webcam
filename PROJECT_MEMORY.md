# Журнал решений проекта

Этот файл фиксирует нетривиальные решения и причины, стоящие за ними — то,
что не видно из самого кода, но важно для дальнейшей работы.

## Виртуальная камера: OBS, а не Unity Capture

Изначально использовался Unity Capture (чистый DirectShow-фильтр). Он
регистрируется через `regsvr32` и работает в OBS/старых приложениях, но
**не виден** современным потребителям камеры (Windows-приложение "Камера",
многие сайты/браузеры) — те опираются на Media Foundation.

Перешли на **OBS Virtual Camera** backend `pyvirtualcam` — он реально виден
браузерам. Установщик ПК-приложения бандлит только сам DirectShow-фильтр
(`obs-virtualcam-module32/64.dll`, ~450 КБ, извлечён из OBS Studio,
GPL-2.0 — см. `pc-app/vendor/obs-virtualcam/NOTICE.md`) и регистрирует его
через `regsvr32` при установке. Полный OBS Studio ставить не нужно.

## Почему camera_worker — отдельный процесс/exe

Попытка создать `pyvirtualcam.Camera(backend='obs')` в том же процессе, где
уже создан `aiortc.RTCPeerConnection` и идёт декодирование видео, **стабильно
падает** с `RuntimeError: 'obs' backend: virtual camera output could not be
started`. Причина — `aiortc`/`av` оставляют процесс в COM-состоянии,
несовместимом с активацией OBS-камеры. Ни другой поток, ни другой event loop
не помогают — конфликт именно на уровне процесса.

Решение: `pc-app/camera_worker.py` — отдельный скрипт, который принимает
сырые RGB-кадры через stdin и создаёт камеру сам, ничего не зная про
aiortc. `main.py` пишет в его stdin. При сборке через PyInstaller это
**два отдельных exe** (`PhoneWebcam.exe` + `camera_worker.exe`, см.
`build.spec`) — у frozen `main.py` нет интерпретатора Python, чтобы
запустить `.py`-скрипт, поэтому `main.py` определяет `sys.frozen` и
запускает соседний exe вместо `[sys.executable, camera_worker.py, ...]`.

## Установщик ПК-приложения

`pc-app/installer.iss` (Inno Setup) требует **прав администратора** —
только ради регистрации DLL в `HKEY_LOCAL_MACHINE`; само приложение потом
работает без админ-прав. Собирается через `pyinstaller build.spec`, затем
`ISCC.exe installer.iss`. Результат: `PhoneWebcam-Setup.exe` — установка
достаточна сама по себе, никаких отдельных драйверов ставить не нужно.

## Подключение телефона: QR-код

PC-приложение показывает QR (JSON `{"s": адрес, "c": код}`) и то же самое
текстом как запасной вариант. Мобильное приложение сканирует QR как основной
способ (`expo-camera`), ручной ввод остался за ссылкой/раскрывающимся блоком.

## Дизайн мобильного приложения

Интерфейс переделан под референс в Figma (тёмный HUD-стиль, "CamLink").
Сознательно **не скопировано 1:1**:
- Название оставлено настоящее — "Phone Webcam", а не вымышленное "CamLink".
- Протокол подписан как "WebRTC", а не "NDI-HX" — это другой реальный
  протокол, которым это приложение не пользуется; писать так было бы враньём.
- Метрики на Live-экране — только реально измеримые:
  - разрешение/FPS — из `track.getSettings()`
  - битрейт и latency — из `RTCPeerConnection.getStats()` (дельта
    `bytesSent` на outbound-rtp video, `currentRoundTripTime` у выбранной
    ICE-пары)
  - заряд батареи — через `expo-battery`
  - таймер сессии — реальный, с момента `status === 'connected'`
- Кнопка Mute Mic — настоящая (аудио теперь захватывается, `audio: true`,
  переключает `track.enabled`). Кнопки "Adjust" нет — под неё нет реальной
  функциональности (настроек), решили не делать decorative-заглушку.
- Экран не гаснет во время стрима (`expo-keep-awake`) — раньше это рвало
  соединение.

## PC-приложение: CustomTkinter, живое превью и запись

Изначально PC-приложение было на чистом Tkinter — одно окно с QR-кодом и
статусом. По запросу приблизить внешний вид к референсу (тёмные карточки
со скруглёнными углами, панель управления камерой, кнопка записи) UI
переписан на **CustomTkinter** — надстройку над Tkinter, а не переход на
PyQt/PySide: визуально достаточно близко к референсу, при этом всего один
дополнительный pip-пакет и минимальные правки `build.spec` (нужно тянуть
JSON-темы CustomTkinter через `collect_data_files`, иначе PyInstaller их не
подхватывает).

Сознательно **не скопировано** с референса:
- Без кастомного safeless-заголовка окна (свои кнопки minimize/close) —
  оставлено нативное окно Windows, чтобы не городить ручной drag/resize.
- Нет иконки-шестерёнки "настройки" — под неё нет реальной функциональности
  (как и с кнопкой "Adjust" в мобильном приложении, см. выше).
- На Live-экране нет заряда батареи телефона и имени устройства ("iPhone 15
  Pro") — WebRTC-канал их не передаёт, а придумывать/подделывать метрику
  решили не делать (тот же принцип, что и в мобильном приложении). Вместо
  этого — реальные PC-side метрики: битрейт и RTT из
  `RTCPeerConnection.getStats()` (аналогично тому, что уже считает мобильное
  приложение на своей стороне), плюс метка качества связи (Excellent/Good/
  Fair) по порогам RTT.
- FPS на HUD-чипе — не то, что заявляет кодек, а реально измеренное число
  кадров в секунду (окно в 1 секунду в `consume_video`).

**Важно про `aiortc.RTCPeerConnection.getStats()`** — он не соответствует
W3C-набору полей, которого можно ожидать по аналогии с браузерным
`RTCPeerConnection.getStats()` (которым пользуется мобильное приложение).
Проверено вручную (два локальных `RTCPeerConnection`, реальный вызов
`getStats()`):
- `inbound-rtp` **не содержит `bytesReceived`** — есть только
  `packetsReceived`, `packetsLost`, `jitter`. Битрейт в `main.py` поэтому
  считается по дельте `bytesReceived` на стате `type == "transport"`
  (агрегирует весь трафик через ICE-транспорт — приемлемо, т.к. на PC только
  один видео-transceiver).
- **Нет статов `type == "candidate-pair"` вообще** — то есть
  `currentRoundTripTime` (RTT) через `getStats()` в aiortc недоступен в
  принципе. Метрика "LATENCY" была изначально задумана по аналогии с
  мобильным приложением, но не сработала бы — на её место поставлена
  "PACKET LOSS" (`packetsLost`/`packetsReceived` из `inbound-rtp`,
  по-настоящему доступны и подтверждены тестом), и от неё же считается
  строка "CONNECTION" (Excellent/Good/Fair по проценту потерь, а не по RTT).
- Если когда-нибудь понадобится реальная задержка PC↔телефon — через
  `aiortc` её не получить, нужен свой ping/pong поверх существующего
  сигнального WebSocket (и на стороне `mobile/src/useCameraStream.ts` тоже).

Цветовая палитра PC-приложения (`COLORS` в `main.py`) — те же hex-значения,
что и в объекте `colors` мобильного `App.tsx`, специально для визуальной
согласованности между приложениями.

**Зеркалирование / поворот / output-разрешение** применяются в одном месте
(`FrameTransformer.apply`) до того, как кадр уйдёт куда-либо — в виртуальную
камеру (`CameraSink`), в запись (`VideoRecorder`) и в превью, — так что все
три места всегда показывают одну и ту же картинку.

**Запись видео** — через `cv2.VideoWriter` (кодек `mp4v`) прямо в основном
процессе: конфликт COM, из-за которого `camera_worker.py` вынесен в отдельный
процесс, специфичен именно для `pyvirtualcam`/backend `obs` и на OpenCV не
распространяется. Файлы пишутся в `~\Videos\Phone Webcam\`, скриншоты — в
`~\Pictures\Phone Webcam\`. Выбран `opencv-python-headless`, а не
`opencv-python` — GUI-функции OpenCV (`cv2.imshow` и т.п.) не используются,
headless-сборка легче и не тащит лишние GUI-зависимости.

## "Connected" не значит "видео идёт" — watchdog на зависшую сессию

Реальный прогон с живым телефоном показал: `main.py` выставляет статус
"Connected" и переключает вид на Live сразу после обмена SDP (offer/answer) —
это НЕ означает, что ICE реально нашёл рабочий путь и видео течёт. Из-за
этого случались два конкретных симптома:
- Экран показывает "CONNECTED" с чёрным превью и "— FPS" бесконечно — ICE не
  смог установить медиапуть (первая причина на практике — Windows Firewall
  тихо блокирует входящий UDP для `PhoneWebcam.exe`/`camera_worker.exe` без
  видимого запроса на разрешение; добавлены явные inbound-правила для
  TCP+UDP на профиле Private).
- "Подключается через раз" — если сессия зависает вот так, `Signaling.busy`
  никогда не сбрасывается программно (сбрасывается только в `finally` после
  закрытия WebSocket), а сокет виснущей сессии закрывается только по
  TCP-таймауту ОС (может быть минуты) — следующая попытка телефона в это
  время получает "busy" и отклоняется.

Решение — `watch_for_stall()` в `main.py`: следит за временем последнего
полученного кадра (`activity["last_frame"]`, обновляется в `consume_video`)
и сам закрывает WebSocket, если видео не пошло вообще за
`FIRST_FRAME_TIMEOUT` (18с — щедро, т.к. только сбор ICE-кандидатов на этой
машине в тесте занимал ~5с) или пошло, но замолчало дольше
`STALLED_TIMEOUT` (6с — тут уже явно живая сессия умерла). Проверено тестом
с двумя локальными `RTCPeerConnection`, где "телефон" отправляет несколько
кадров и зависает — сессия корректно сбрасывается, следующее подключение
проходит.

## Реальная регрессия качества видео: numpy-копия после mirror/rotate

Пользователь сообщил, что до этой сессии (без Mirror/Rotate/записи вообще)
видео шло нормально, а после моих изменений — плохо. Замерил по кадрам
(1920×1080, бенчмарк на этой машине):
- `FrameTransformer.apply()` с mirror или rotate: **17-21мс/кадр** — почти
  весь бюджет в 33мс на кадр при 30 FPS. Причина — `frame[:, ::-1, :]` и
  `np.rot90()` создают view с обратным/переставленным страйдом, а
  `np.ascontiguousarray()` в конце копирует его поэлементно (кэш-недружественный
  паттерн), а не быстрым memcpy.
- `VideoRecorder.write()` во время активной записи: **22-53мс/кадр**
  (`cv2.cvtColor` + синхронная запись на диск прямо в asyncio-потоке, который
  также кормит виртуальную камеру).

Оба места — на event loop потоке `consume_video`, так что любой из них сам
по себе уже мог душить кадры (и потенциально мешать aiortc успевать
обрабатывать RTP/RTCP в том же потоке).

Исправлено:
- `FrameTransformer.apply()` переписан на `cv2.flip`/`cv2.rotate` вместо
  numpy-срезов — они возвращают уже contiguous-массив, копировать после них
  ничего не нужно. Направление поворота проверено на тестовом паттерне —
  совпадает с прежним `np.rot90` пиксель-в-пиксель. Результат: mirror
  17.5мс→3.3мс, rotate 21.3мс→8.2мс.
- `VideoRecorder` теперь пишет на диск в отдельном потоке через
  `queue.Queue` (maxsize=8, при переполнении кадр просто дропается) —
  `write()` из asyncio-потока стал не блокирующим постановкой в очередь
  (22мс → 0.01мс), а `stop()` дожидается `thread.join()`, чтобы файл гарантированно
  дозаписался. Проверено `cv2.VideoCapture`-читкой обратно — все кадры на
  месте, размер и разрешение верные.

Важно: если после этого фикса пользователь при "чистых" настройках (без
mirror/rotate/записи, output = source) всё ещё видит плохое качество —
это, скорее всего, уже не код: `report_stats()` в тех прогонах показывал
`packetsLost`/`packetsReceived` как "—" (ни одного видео-пакета не
засчитано вообще), что указывает на реальную проблему ICE-соединения
(Wi-Fi/роутер), а не на локальную производительность.

## CONNECTION-чип теперь показывает реальное состояние ICE, не только "—"

После обоих фиксов выше пользователь всё ещё получал "CONNECTED" с пустым
превью — но уже с Mirror/Rotate/записью выключенными, то есть код точно не
виноват. Проблема в том, что раньше "CONNECTION" в HUD показывал качество
только когда УЖЕ пришёл хотя бы один видео-пакет (считалось из
`packetsLost`/`packetsReceived`) — если пакетов вообще ноль, чип молча
показывал "—" и было невозможно отличить "ещё идёт ICE-проверка" от
"ICE не смог найти путь вообще".

Добавлено: `pc.on("connectionstatechange")` → `app.push_ice_state(...)`.
Пока не пришло ни одного видео-пакета, "CONNECTION" показывает реальное
состояние `RTCPeerConnection.connectionState` (`Connecting…` / `Connected
(no media yet)` / `ICE failed` / `ICE disconnected`) с цветом
(жёлтый/зелёный/красный); как только пошли настоящие пакеты, чип
переключается обратно на Excellent/Good/Fair по потерям — `report_stats`
теперь передаёt `quality=None`, когда `loss_pct` ещё нет, и `_poll` не
затирает ICE-текст в этом случае. Проверено на связке из двух локальных
`RTCPeerConnection` через настоящий `Signaling.handler` — событие
`connecting`→`connected` доходит до приложения корректно.

Если следующий скриншот покажет "ICE failed"/"ICE disconnected" —
это окончательное подтверждение, что проблема в сети (роутер/Wi-Fi/изоляция
клиентов), а не в приложении.

устанавливается вручную (пересборка подписи/сайдлоад — как раньше).

- Разрешение видео с телефона сейчас — то, что камера отдаёт по умолчанию
  (обычно ~1280×720), явных constraints `width`/`height` в

  **не сделано**, добавить `video: { facingMode, width: { ideal: 1920 },
